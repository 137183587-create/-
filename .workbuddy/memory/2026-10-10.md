## 全站卡片动效改为「可逆 / 滚动重播」
- 用户诉求：所有卡片动效要可逆，且**再次划过页面时动效能再次出现**，由鼠标滚动触发。

## GradientCarousel 滚轮调慢 + 调平滑（目标值 + rAF 缓动跟随模型）
- 用户反馈"间距刚好，但滚动速度要更慢、更平滑"。
- **问题根因**：原实现滚轮/拖拽**直接 `setOffset`**，靠 CSS `transition: transform .55s` 兜底 —— 连续滚动时 transition 被不断打断重启，表现为"急、卡、串"。
- **改法（关键架构）**：改为**目标值 + rAF 指数缓动跟随**双缓冲：
  - 新增 `targetRef`（目标）与 `offsetRef`（渲染值）分离；滚轮/拖拽/惯性**只写 target**，一个常驻 rAF 循环里 `next = cur + (tgt-cur)*0.09` 逼近并 setOffset。
  - 滚轮单次事件**限幅** `clamp(raw, -0.34, 0.34)`，系数由 `*0.02` 降到 `*0.012` → 滚速更慢、防触控板大 delta 突跳。
  - 拖拽改写 target（跟手），松手惯性改为**衰减 target**（`frictionFactor`），停后吸附整数卡；`goTo`（键盘/圆点）保持立即跳转不脱手。
  - **配套移除 CSS** `.gcar__item` 的 `transition: transform` —— rAF 插值已提供平滑，再叠 CSS 过渡会双重延迟出拖影。opacity 过渡保留。
- **可复用规律**：滚轮驱动的连续动画，"CSS transition 兜底" ≠ 平滑；正确做法是 **ref 存目标 + rAF 缓动跟随 + CSS 不参与 transform 过渡**，否则会出现打断重启与拖影。
- 构建通过（JS 362.30KB / CSS 79.46KB）。预览 http://localhost:5174/ 。仍需用户目视手感。

## 修 bug：SpinShutter 环轨「啥也不显示」（3 个叠加问题）
**症状**：/medical 页 AI 动画区完全空白，只有标题「AI 动画」+ 底部圆点 + caption 文字可见，卡片一张都不显示。

**根因 2（架构级）**：卡片 transform 里的角度 `off` 在 render 时用 `angleRef.current` 计算，但自转只改 CSS 变量 `--spin`、**不触发 React 重渲染** → 角度永远停在初始值，卡片不会跟着转。

**根因 3（几何算错）**：`ringRadius=1000` 与 `sz=size=0.3` 重复相乘 → 实际环半径仅 300px，而 31 张卡的弧距 60.8px vs 卡宽 533px，**严重重叠等于看不见**。

- **几何铁律（可复用）**：n 张卡均分整圈且不重叠 → 环半径必须 `≥ n×卡宽/(2π)`；n 越大环半径线性增长。别用"固定环半径 + 固定卡宽"，那必然重叠。

## 修bug：InfiniteGallery「没有伪 3D 空间感」（卡片挤成一排）
**症状**：图像场看起来是一排小图挤在中间，完全没有纵深（原组件应有明显的伪 3D 空间）。

## 滚动前进/后退更「平滑缓慢」：单层缓动 → **双层平滑（施力模型）**
**问题**：上一版只有第 2 层（相机位置缓动），但**滚轮是直接跳写 targetZ**（一次 deltaY=120 → target 瞬间跳 96px）。缓动只能"追"，追不上起跳的突兀 → 观感仍偏生硬。
**方案：改成「施力模型」（物理正确，输入本身也平滑）**
- **第 1 层 输入平滑（新增）**：滚轮不再写 targetZ，改为给 `velZ` **施加冲量**；rAF 里 `targetZ += velZ`，然后 `velZ *= wheelFriction`（按 dt 归一化）衰减 → 相机是被「推动」的，速度受限、连续无跳变。
- **第 2 层 位置平滑（保留）**：`camZ += (targetZ-camZ)*k`，`k=1-(1-smoothing)^(dt/16.67)`。
- 两层叠加 = 起步软 / 中段稳 / 收尾拖。
**关键设计：预算扣减与施力大小必须解耦**
新增两个参数各司其职（之前只有一个 `wheelToBudget` 同时干两件事，导致相机位移=预算扣减，参数无法独立调）：
- `wheelToBudget`（预算换算，0.8）：决定「滚几次后交还页面」——只影响拦截与否。
- `wheelPulse`（施力换算，0.22）：决定「滚一次滑多远」——只影响相机速度。
- **踩坑**：曾把冲量也用 wheelToBudget → 一次滚轮总位移高达 960px，预算1980px 只需 2 次滚轮就到底，画面"飞"过去；解耦后一次滑行 330px，需 7 次滚轮走完预算，节奏才对。
**拖拽同样改造**：`velZ` 拆成 `velZ`（滚轮）与 `dragVel`（拖拽）两个独立 ref——原先共用一个会导致拖拽与滚轮互相干扰。

## 修三个问题：①点击无响应 ②滚动时卡片内容闪跳 ③不无限 ④加退出三角按钮
### ① 点击无响应 —— 根因是 `setPointerCapture`
- **症状**：点卡片没反应，聚焦层不出现（`focusLayerShown:false`）。
- **根因**：`onPointerDown` 里 `e.currentTarget.setPointerCapture(pointerId)` 把指针**捕获到 .igal 根元素**，后续 `click` 事件被父元素截走，卡片上的 `onClick` 永远不触发。
- **修法**：**移除 setPointerCapture / releasePointerCapture**，改用「位移阈值」区分点击与拖拽——新增 `moved` ref 累计按下位移，`<6px` 视为点击（让 click 正常发生），`≥6px` 视为拖拽（`handleClick` 里 `if(moved>6) return` 抑制误触发）。
- **排查教训**：① 用合成 `dispatchEvent(new PointerEvent/WheelEvent)` 时，React 状态更新是异步的，**点完立刻查 DOM 会误判"没反应"**，必须 sleep 1.5s 再查；② 判断"是否被遮挡"用 `document.elementFromPoint(cx,cy)` 最直接（比逐个猜 z-index 快）。
- 实测：点击后聚焦层出现、有「▶ 播放视频」按钮、标题正确。
### ② 滚动时卡片内容闪跳（用户："往前一滚动卡片中的视频就会跳成别的"）
- **根因**：`imgIdx`公式里含 `(camCell + gz)*31`，相机每跨一格 `setCamCell` 触发 planes 重算 → **整场 75 张卡瞬间轮换**，看起来是闪屏而非穿行。
- **修法**：`imgIdx`改为**只由空间位置决定**：`Math.abs(Math.round(ry*47 + gx*13 + gz*101 + j*5)) % total`，**彻底移除 `camCell`**（连带删掉 `camCell` state、`setCamCell`、`lastCell` 跨格逻辑，及 planes 的 camCell 依赖）。
- 实测：滚 8 次滚轮后 **20/20 卡片内容完全不变**，相机移动 175px。滚动的视觉变化现在**纯粹来自相机位移 + 透视缩放**，内容稳定，走到远处才自然离开视野。
- **规律：无限感不等于"内容不断换"。"换格换图"是闪屏，"同图随相机移动出视野"才是真穿行。**
### ③ 真正的无限滚动
- **根因**：`targetZ` 被 `clamp(0, scrollBudget*cell)` 锁死 → 最多走 4 格（1980px）就到头。
- **修法**：移除 clamp 上限，`targetZ += velZ` 可无限累加。无限循环本已由渲染层保证：`--cam-local = camTotal % cell`（0→495→0→495 锯齿循环）+ 网格复用。
- 实测 node 验证取模：camTotal 0→124→446→**0**(1格)→…→10格仍为 0，循环正确。
- **注意**：滚轮「预算制」仍保留（`budgetRef` 只用于**判断何时把滚轮交还页面**，不再限制相机位移）——两者已解耦：`wheelToBudget` 管交还时机，`wheelPulse` 管滑行距离，相机本身不限。
### ④ 底部半透明倒三角「继续浏览」按钮
- JSX `.igal__exit`（`z-index:940`，高于雾罩 900），CSS 三角形（`border-top:12px solid rgba(255,255,255,.62)`，无图片），毛玻璃背景 + hover 变金色 + `igalExitPulse` 呼吸动画（3.2s 无限循环，hover 暂停）。
- `handleExit()`：**清空 `budgetRef`/`velZ`/`dragVel`** → 下个滚轮不再被拦截（页面滚动立刻恢复），再 `window.scrollTo({top: 区块底+vh*0.25, behavior:'smooth'})` 直接进入下一节。
- props：`showExit`（默认 true）、`onExit`（自定义回调，不传走默认行为）。
- **设计意图**：全屏沉浸区块独占滚轮，用户可能不想滚到底 → 给**显式出口**，而非只能"一直滚到交还"。
构建：CSS 74.28KB / JS 365.41KB (gzip 127.66KB)。

## 修「滚轮一卡一卡的」：--cam-local 取模 → **卡片自流动 + 出界回收**
**症状**：滚轮控制不连贯，一格一格地跳。用户明确反馈"这个控制好像不是循环的，滚轮控制一卡一卡的"。
**根因（两个，都必须改）**：
1. **整体平移 + 对格距取模**：`--cam-local = camTotal % cell`，相机每走满一格（495px）整场就跳回原点。虽然网格排列重复、肉眼看似连续，但**视觉上是"跳一下"** → 卡顿感。
2. **`.igal__cell` 上有 `transition: filter .35s, opacity .35s`**：rAF 每帧写入 transform/opacity/filter 时，transition 让**每帧写入都带 0.35s 滞后** → 动画永远追不上、粘滞。这是不连续的**另一半原因**，容易漏掉。
**修法（架构级改动）**：
- **相机推进不再动 stage**，改为**每张卡自己在 z 轴流动**：rAF 里遍历 `cellRefs`，`z = p.z + camTotal`，直接写 `el.style.transform`。
- **出界回收**：`recycleZ = Math.max((viewRange+1)*cell, fogFar*0.55)`；`if (z > recycleZ) z -= cycleSpan; else if (z < -recycleZ) z += cycleSpan`，`cycleSpan = recycleZ*2` → 飞出视野的卡循环到另一端重生，**无限且全程连续**。
- **雾效/zIndex 必须跟随实时 z**（不能只用初始 p.z），否则卡被搬到远端后明暗不变会很假；在 rAF 里一并写 opacity/filter/zIndex。
- **CSS 移除 `.igal__cell` 的 transition**，加 `will-change:transform,opacity`；hover 动效保留在内部 `.igal__img` 上。
- stage transform 去掉 `var(--cam-local)`，只留指针漂移 `--cam-x/--cam-y` + rotateX(8deg)。
**回收不可察的关键（防"新闪跳"）**：
- `recycleZ` **必须由 fogFar 推导**，不能随手取格距倍数——若回收点 opacity 还 >0，卡被搬走的瞬间用户会看到"卡片闪现"。
- 加**强制淡出兜底**（比调 fogNear/Far 数值可靠）：`fadeOut = clamp((recycleZ - dist)/(cell*0.5), 0, 1)`，`opacity = (1 - ft*0.8) * fadeOut`，回收点处 opacity 恒为 0.000。
- 实测可见度曲线：z=0→1.000、495→0.814、990→0.581、1238→0.465、**1485→0.000** ✓
- node 验证连续性：相机 0→3 格，卡 z 轨迹**跳变次数 0**（阈值 150px）✓
构建：CSS 74.25KB / JS 365.91KB。预览 http://localhost:5176/medical-visualization 。

## 卡片「无尽随机刷新」：回收时换图+换位置+换缩放
**用户诉求**：卡片可以一直往后随机刷新（不只是循环重复同一批内容）。
**核心设计**：卡被回收（飞出 ±recycleZ、循环到另一端）的**那一刻**，
因为此时它在 `opacity=0` 的远端、用户完全看不见 → **趁机换一套新内容**：
- 换图：`p.imgIdx = (p.imgIdx + 1 + floor(rand(s) * (total-1))) % total` ——「步进 + 随机」保证既不会原地不动、也保证相邻两次不重复。
- 换位置抖动：`p.x/p.y = p.gx*cell/cellY*... + (rand-0.5)*cell*0.9`（`gx/ry` 已在 planes 里保留）→ 每次重生散落位置都不同。
- 换缩放与尺寸：`p.scale = 0.72 + rand()*0.62`，并同步写 `--w/--h/--image-radius` → 大小变化更多样。
**性能关键：直接改 DOM，不走 React**
- `refreshPlane(p, i)` 内用 `el.querySelector('img').src = ...`、`el.setAttribute('aria-label')`、`el.querySelector('.igal__label').textContent`、`el.style.setProperty('--w'/'--h'/'--image-radius')`。
- **原因**：一帧内可能有十几张卡同时回收，若用 setState 会触发整场重渲染、明显掉帧。
- 新增 `recycleSeq` ref 作递增种子（`seq*977 + i*131`），保证同一帧多张卡不会拿到相同新图。
- rAF effect 依赖里补上 `refreshPlane`（useCallback 引用变化会重启 rAF）。
**效果**：往远处滚时，远端不断涌现「没见过的卡」→ 真正无尽。且因为刷新点在完全不可见处，**不会引入任何闪跳**（与前一轮修的"一卡一卡"不冲突）。
验证：node 模拟一张卡连续 12 次回收，**相邻重复 0 次**、覆盖 9 种不同内容。
构建：JS 366.70KB (gzip 128.16KB)。预览 http://localhost:5176/medical-visualization 。

## 修「卡片乱跑」：回收刷新时x/y 抖动过大 + 淡出带太窄
**症状**：加入「无尽随机刷新」后，卡片位置疯狂乱跳（用户："现在在乱跑"）。
**根因（主因是抖动幅度）**：
- `refreshPlane` 里 `p.x = p.gx*cell + (rand-0.5)*cell*0.9` → **±446px，而格距才 495px**，
  意味着每次回收随机位置几乎能跨越一整个格子。用户看到的就是"卡片突然跳到别处"。
- **初始 planes 的抖动也是 0.9**（这是上一轮为"打散网格感"设的），当时是对的；
  但**一旦引入"回收刷新"，0.9 就变成了乱跳**——两个需求（初始散落 vs 刷新稳定）用了同一个参数。
**修法**：
1. **抖动统一收窄到 0.32**（±158px，格内微移），初始 planes 与 refreshPlane **两处同步改**——
   不同步会出现"初始乱、刷新后反而稳"的割裂感。
2. **淡出带从 248px 加宽到 495px（整整一格）**：新增 `fadeFrom = recycleZ - cell`，
   `fadeOut = clamp((recycleZ-dist)/(recycleZ-fadeFrom), 0, 1)`。卡片在移动中一路淡到 0，
   回收点处 opacity 必然为 0 → 换位置/换图永远发生在不可见处。
3. **修纵向重叠**：发现 `cellY=330`（系数 0.2）**小于图高 105px 太多**（净空仅 105px），
   同列相邻层必然重叠。改 `cellY` 系数 0.2→**0.24**（396px）+ `imageSize` 7→**6**（图160×90），
   净空 306px、最坏重叠 68px，观感疏朗。
**规律（重要）**：「初始散落感」和「刷新稳定性」对抖动幅度的要求是**相反的**——
- 只要初始散落 → 抖动要大（0.9）
- 一旦加入回收刷新 → 抖动必须小（0.32），否则每次重生都是"跳位"
两者冲突时，**优先稳定性**，散落感可以靠「随机缩放 + 淡出层次」补足。
另外淡出带宽度不只是美观问题：**它是"不可见保证"的工程手段**，宽度应 ≥ 一个格距。

## 修「推进一段距离后乱刷」：回收时未写回 p.z → 每帧重复回收（真 bug）
**症状**：上一轮收窄抖动后短期正常，但「往前推进一段距离之后还是会乱刷」——滚动一段时间后卡片疯狂换图换位。
**根因（关键教训：回收时必须写回基准值）**：
```js
let z = p.z + camTotal                 // p.z 是静态基准
if (z > recycleZ || z < -recycleZ) {
  z += z > recycleZ ? -span : span    // ← 只改了局部变量 z
  refreshPlane(p, i)                  // 每帧都触发！
}
```
- `p.z` 是卡片的**基准 z**，只在挂载时按网格层算一次。
- 回收时**只改了局部变量 `z`，没写回 `p.z`** → 下一帧重新计算 `p.z + camTotal`
  得到的**还是同一个越界值** → 再次进入 if → **每帧都回收、每帧都 refreshPlane**。
- 所以现象是「刚滚还好，推进一段后越来越乱」——因为 camTotal 越大越容易持续越界。
**修法**：回收时同步写回 `p.z = z`，让卡片从新位置继续正常流动，
下一次越界要等相机再走完整个 span。
```js
if (z > recycleZ || z < -recycleZ) {
  z += z > recycleZ ? -span : span
  p.z = z            // ★ 关键：写回基准值
  refreshPlane(p, i)
}
```
**验证（node 复现+修复对比）**：相机连续走 1500px（60帧×25px）
- 修复前：**41 次刷新**（几乎每帧一次）→ 疯狂乱刷
- 修复后：**1 次刷新**（符合 span=2970px 的预期）
实测页面：滚 40 次滚轮后 75 张卡稳定、16 张图仍在用（内容仍变化，非卡死）。
**核心规律（务必记住）**：
> **环形回收/循环复用类逻辑里，「当前偏移」和「基准值」必须区分**。
> 只改局部计算出的当前值而不写回基准，会导致条件**每帧重复成立** → 无限重复执行。
> 凡是 `if (越界) { 重置 }` 这类逻辑，重置必须写回**下一次计算会读的那个变量**。
**附带验证**：`span/cell = 2970/495 = 6.000` 恰好整数倍 → 回收后各卡仍保持整数格间距，
层结构不会逐渐失序。若 span 不是 cell 整数倍，滚动久了会出现层间距错乱。

## 改为「无限长廊」循环：放弃随机刷新，回归绝对格号取模（重要方向修正）
**用户诉求**："难道不能做循环吗，无限长廊" —— 明确指出要的是**有规律的循环**，不是随机刷新。
**方向修正（关键教训）**：
之前为解决"内容重复"走了「回收时随机换图 + 随机换位置」的路子，虽然修掉了乱刷/乱跑，
但**丢失了"长廊"的结构感**——随机内容没有规律，看起来像在乱换。
**最终方案（更优雅、更简单）**：
- **图片索引改用「绝对格号」取模**：`absIdx = gz*(COLS*ROWS) + gy*COLS + cIdx`，
  `imgIdx = ((absIdx % total) + total) % total`（注意负数要 `+total` 两次）。
  → **第 N 格永远显示第 (N mod total) 张图**，往前滚时远处按顺序涌现新内容，走完一轮自然重复。
- **`refreshPlane` 改名 `recyclePlane`，去掉全部随机**：
  回收时按 `camDirRef`（相机方向 +1/-1）落到`nextGz = p.gz ± 1`，
  然后**用与 planes 初始布局完全相同的公式**重算 gz/imgIdx/x/y/scale。
  → 同一格号的位置与缩放恒定 → **天然不会跳位乱跑**，也不需要随机种子。
- planes 里补存 `gz / gy / cIdx` 字段供回收时推算；新增 `camDirRef` 记录滚动方向，
  保证长廊**始终朝滚动方向延伸**（往前滚就不断有新层从远端补上）。
**验证**：第0/1/2 层图索引依次为 `0..14`、`15,0..13`、`14,15,0..12` → 每层不重复、逐层顺序推进 ✓
**核心认知（值得长期记住）**：
> **"无限"不等于"随机"。** 随机刷新解决了"重复"但破坏了"秩序感"，反而像在乱换。
> 正确的无限循环是 **「绝对格号取模」**：内容与空间位置建立确定性映射，
> 往前滚自然推进、走到头自然回到起点——**既无限、又有规律、又不跳变**。
> 之前多个"乱跑/乱刷"问题（抖动过大、每帧重复回收）本质都是**引入了不该有的随机性**。
构建：JS 366.87KB (gzip 128.23KB)。预览 http://localhost:5176/medical-visualization 。

## MasonryCards 改为「完整显示视频」（object-fit contain）
**用户诉求**："尽可能把视频显示全"
**问题**：原来用 `object-fit: cover` 铺满卡片 → **画面被裁切**（视频上下或左右被切掉）。
**解法（两层图）**：
1. **前景层 `.ms__img--fg`**：`object-fit: contain` —— 完整显示视频画面，**绝不裁切**。
2. **背景层 `.ms__img--bg`**：同一张URL、`inset:-12%` 放大 124%、`filter: blur(22px) brightness(.5) saturate(.85)`
   → 填充 contain 留下的空档，避免出现生硬黑边（这是视频卡片的通用做法）。
   两层同一 URL，浏览器只请求一次，无额外网络开销。
3. **卡片比例按视频真实宽高比自适应**：图片 `onLoad` 里读 `naturalWidth/naturalHeight`
   → 写回 `--ms-aspect`（直接改 DOM style，不走 setState）。
   **contain 时零浪费**：卡片比例 == 视频比例 → 上下不出现空档，背景层仅作安全兜底。
4. **保留瀑布流错落感**：因为所有视频都是 16:9，比例统一会让布局过于规整，
   加 `.ms__item--alt { padding-top: 26px }`（偶数项微纵向偏移）保持错落节奏。
**踩坑**：
- 两个 `<img>` 曾共用 `className="ms__img"`（背景层多写一个修饰类），
  导致 CSS 选择器 `.ms__img` 同时命中两层，**前景图样式被背景层覆盖 → 只看到虚化背景、看不到画面**。
  **修法：两层各用独立类名 `ms__img--bg` / `ms__img--fg`，不要让一层是另一层的"超集"。**
  （截图才发现：肉眼看"全是模糊图"才定位到，不是报错。）
- `node -e` 脚本里写注释含反引号 + `object-fit:` 会被 bash 当命令执行 → `command not found`。
  **在 node -e 里做字符串替换时，替换文本务必避开反引号与冒号开头的裸词。**
**效果**：16 张卡全部 `object-fit: contain`、画面完整、错落节奏保留、8 张带 alt 偏移。
构建：CSS 73.14KB / JS 360.93KB。
